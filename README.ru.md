<h1 align="center">project-memory</h1>

<p align="center">
  План, доска задач, журнал решений, выводы проекта и передача контекста между сессиями для каждого git-репозитория.<br>

</p>

## Зачем

Claude Code забывает всё между сессиями. На любой работе дольше одного захода это стоит дорого:

- каждая новая сессия начинается с «на чём остановились?» и повторного чтения репозитория;
- причины прошлых решений теряются, и закрытые вопросы обсуждаются заново;
- два worktree одного репозитория ничего не знают друг о друге и могут взять одну и ту же работу;
- план, написанный другим инструментом (superpowers, gstack, plan mode), расходится с тем, что сделано.

project-memory держит одну небольшую доску на репозиторий и вставляет её сводку, не длиннее 40 строк,
в начало каждой сессии. Доску Claude ведёт сам: заводит задачи, двигает статусы, записывает, что сделано
и что дальше, и фиксирует решения вместе с отвергнутыми вариантами.

## Установка

Нужны Node ≥ 20 и git. Работает на macOS, Linux и Windows. Зависимостей нет.

```
/plugin marketplace add ZizzX/claude-project-memory
/plugin install project-memory@project-memory
```

Перезапустите Claude Code (новый процесс, `/clear` не подойдёт), чтобы загрузились хуки.

**Обновление:** когда новая версия уже есть на этой машине или вышла в репозитории, сводка сессии сама скажет:

```
[pm] update available: 0.3.0 → 0.3.1 — say "update the plugin", "later", "never" or "update it yourself"
```

Скажите **«обнови плагин»** — Claude поставит новую версию и напомнит перезапуститься; **«позже»** —
молчит 7 дней (релиз новее засноуженного всё равно напомнит о себе), **«не напоминай»** — молчит навсегда,
**«обновляй сам, не спрашивай»** — дальше Claude ставит новые версии сам и всё равно сообщает, что поставил.
Ответ хранится в `git config --global`: `pm.updateNotify` (`ask` | `auto` | `never`) и `pm.updateSnoozeUntil`.
Без вашего «да» ничего не ставится.

Руками это:

```
/plugin marketplace update project-memory
/plugin update project-memory@project-memory
```

После этого снова перезапустите Claude Code.

Проверка стоит двух чтений локальных файлов — копии маркетплейса, которую Claude Code и так держит у себя.
Раз в сутки плагин дополнительно читает выпущенный `plugin.json` по HTTPS, отдельным фоновым процессом,
который никогда не задерживает сессию; выключается через `git config --global pm.updateCheckNetwork false`,
локальная проверка при этом продолжает работать.

## Быстрый старт

1. Откройте репозиторий и начните настоящую работу: «делаем импорт CSV». Для нетривиальной многошаговой работы
   Claude сам создаст доску (`pm init`), заполнит `PLAN.md` и подтянет уже существующие планы. Можно и прямо:
   «создай доску».
2. Скажите **«разбей»**. Claude заведёт задачи с порядком и зависимостями и приложит ссылку на подробный план.
3. Скажите **«что дальше?»**. Claude возьмёт первую готовую задачу и запишет, как он её понял.
4. Работайте как обычно. Заканчивая, скажите **/close**: Claude закроет или залогирует каждую задачу с точным
   следующим шагом, запишет, чему научила сессия, и выберет задачу, с которой начнётся следующая.
   («закончили» само по себе только записывает следующие шаги.)
5. Делайте `/clear` или возвращайтесь завтра в любом worktree. Сессия откроется со сводкой и продолжит.

`board.html` (ссылка есть в сводке) показывает канбан, который обновляется каждые 10 секунд и сохраняет раскрытые карточки и прокрутку.

## Четыре способа обращения

| Способ | Что это | Кто пользуется |
|---|---|---|
| **Хуки** | Срабатывают сами: сводка при старте сессии, напоминания, страховочные заметки | никто, они просто работают |
| **Фразы** | Обычный текст в чате, например «что дальше?» | вы |
| **`/pm`** (или `/project-memory:pm`) | Скилл: протокол, по которому Claude действует в каждой ситуации | Claude; вы, чтобы прочитать правила |
| **CLI `pm`** | Команды, которые меняют доску | Claude; вы, когда хочется |

Все команды и фразы разом:

```
node ~/.claude/plugins/marketplaces/project-memory/scripts/pm.mjs help
```

### `pm` в обычном терминале

CLI не требует Claude Code. Скажите в сессии **«добавь алиас pm»** или один раз запустите:

```
node ~/.claude/plugins/marketplaces/project-memory/scripts/pm.mjs alias
```

(Плагин поставлен из локальной папки? Путь возьмите из строки `CLI:` в сводке сессии.)

Команда добавляет `pm` во все профили PowerShell и в Git Bash на Windows, в `~/.zshrc` или `~/.bash_profile` на macOS,
в `~/.zshrc` или `~/.bashrc` на Linux и печатает, какие файлы изменила. Повторный запуск безопасен, а `pm`, заданный
вами вручную, она не трогает. Откройте новый терминал: `pm board` печатает путь к `board.html`, `pm help` — всё остальное.
Если PowerShell не загружает профиль, разрешите это один раз: `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned`.

## Что говорить

| Вы говорите | Claude делает |
|---|---|
| «что дальше?» | `pm next --options`, затем спрашивает, что брать: текущую задачу, задачу из очереди, другой эпик или своё — у каждого варианта строка описания |
| «бери следующую» | `pm next`: берёт первую готовую задачу направления этого worktree, сначала пишет `## Understanding` |
| «разбей» | Заводит задачи с `--order`, `--deps`, `--epic`; детали кладёт в файл плана и ссылается на него |
| «запомни …» | Записывает ровно в одно место: решение, auto-memory или `## Understanding` задачи |
| «ждём …» | `status=waiting` с причиной; задача уходит из Ready |
| «закончили», «продолжим в новой сессии» | Пишет `did` / `next` во все активные задачи worktree, обновляет фокус |
| `/close`, «слил», "wrap up" | Закрывает сессию: каждая задача worktree закрыта или залогирована с `next:`, ретро, задача, с которой начнётся следующая сессия — см. [Закрытие сессии](#закрытие-сессии) |
| «что узнали нового», "what did we learn" | Ретро: записывает вывод (`pm learn add`) или говорит, что выводов нет (`pm learn none`) — см. [Выводы](#выводы) |
| «в следующей сессии берём T-007», "next session starts with T-007" | `pm next`: сводка начинается с этой задачи, пока её не возьмут |
| «аудит доски», "audit the board" | `pm audit`: устаревшие задачи, мёртвые worktree, неиспользуемые выводы; `--fix` для механической части — см. [Аудит](#аудит) |
| `/done`, «готово, закрываем» | Сверяет разговор с критерием готовности и запускает `pm done`: задача `done` или ждёт мерджа и закрывается сама, когда он случится — см. [Закрытие сессии](#закрытие-сессии) |
| «план меняется» | Правит `PLAN.md`, добавляет строку в Changelog, фиксирует решение |
| «отмени правку доски», «откати» | Отменяет это изменение самой доски через git |
| «откати код T-007», «удали изменения T-007» | Показывает блок `undo:` из `pm show T-007` вместе с рисками, ждёт вашего «да» и откатывает коммиты задачи в новой задаче отката, в ветке `revert/T-007` |
| «вернись к состоянию до T-007» | Сначала предлагает `git switch -c before/T-007 <base>` — ничего не теряется; разрушающие варианты только если вы их попросите |
| «добавь алиас pm» | `pm alias`: `pm` работает в любом терминале, не только в Claude Code |
| «включи синхронизацию доски», «подключи доску» | Показывает, куда будет отправлена доска, и ждёт вашего «да» |
| «обнови плагин», «позже», «не напоминай», «сам обновлю» | Ответ на строку `[pm] update available`: поставить новую версию, отложить на 7 дней, замолчать навсегда или просто показать команды |
| «обновляй сам, не спрашивай» | `pm.updateNotify=auto` — дальше Claude ставит новые версии без вопроса и сообщает, что поставил |

Просто «откати T-007» — двусмысленно, поэтому Claude переспросит, что именно: правку доски, код задачи
или состояние репозитория до неё. Плагин сам не выполняет разрушающих git-команд над вашим кодом — он
печатает точную команду и ждёт.

Когда для задачи создан MR/PR, скажите об этом или выполните `pm set T-NNN pr=<url>`: `pm show` после этого
читает его состояние, SHA слияния и автора, а блок отката нацеливается на merge-коммит, а не на отдельные коммиты.

Английские фразы тоже работают: "what's next?", "take the next one", "break it down", "remember …",
"we're done", "done, only merge left", "continue in a new session", "close the session", "wrap up",
"what did we learn", "next session starts with T-007", "audit the board", "the plan changes", "waiting for …", "undo that",
"undo the code of T-007", "go back to the state before T-007", "enable board sync", "connect the board", "add the pm alias",
"update the plugin", "later", "never", "update it yourself".

Каждый ход, в котором менялась доска, заканчивается одной строкой на вашем языке, например
`доска: T-003 → done · новая T-007 «миграция данных» (после T-005) · D-004`.

## Сводка сессии

```
[pm] my-app · epic APP-12 · focus: import pipeline, parser done · board: file:///…/pm/board.html
Your worktree (feature-csv):
  T-003 CSV import [in_progress] → next: handle empty rows (2026-09-12, feature-csv)
Elsewhere: T-008 Export to XLSX @ feature-export
Ready: T-004 validation ← next · T-006 export · +2 in other epics (pm ready --all)
Waiting: T-005 ← answer about date format
Awaiting merge: T-002 (#14)
Merged, still open: T-001 (#12) — ask the user, then pm reconcile --yes <the ids they confirm>
Epics: APP-12 4/6 · APP-15 2/2
Decisions: D-004 Store board outside branches · D-003 Own format
Learnings: L-007 CI translation keys fail while local passes
CLI: node "…/scripts/pm.mjs" <command>
Rules: …
```

| Строка | Что значит |
|---|---|
| заголовок | проект, эпик этого worktree, его строка фокуса из `PLAN.md`, ссылка на доску |
| Your worktree | открытые задачи, взятые здесь, с последним записанным следующим шагом |
| Elsewhere | задачи в работе в других worktree, их не брать |
| Ready | задачи `todo`, у которых все зависимости выполнены, в эпике этого worktree. Задача, выбранная в `/close`, идёт первой с пометкой `← next` (`← next (after PM-009)`, пока её зависимости открыты) |
| Waiting | задачи, заблокированные чем-то вне доски, и чем именно |
| Closed after merge | задачи в `review`, закрытые на этом старте сессии: их мердж уже виден |
| Awaiting merge | задачи в `review`: готовы, остался только мердж |
| Merged, still open | смёрженные задачи, которые не отметили готовыми: Claude спросит, прежде чем закрыть |
| PR conflict | `pr` задачи открыт из другой ветки, чем у задачи; `pm reconcile` покажет, как исправить |
| Epics | открыто / всего по каждому направлению |
| Decisions | три последних решения |
| Learnings | до 5 активных выводов по задачам этого worktree (иначе самые свежие по `last`), только id и заголовок |
| Promote | выводы, готовые стать правилом, например `L-003 ключи падают в CI (seen 4 in 3 tasks)`, затем подсказка предложить правило; только если такие есть |
| `[pm] audit: N findings` | раз в неделю, если аудит что-то нашёл: запустите `pm audit` |

Сводка никогда не длиннее 40 строк. Подробности остаются в файлах и читаются, только когда нужны.

## Несколько направлений в одном репозитории: эпики

Доска одна на репозиторий, поэтому несвязанная работа в разных worktree делит её. Дайте каждому
направлению **эпик**: свободный ключ на его задачах. Обычно это ключ эпика или тикета в Jira/Linear,
либо короткий слаг:

```
pm task new --title "Parser" --epic APP-12 --links docs/plans/csv-import.md
```

- **Эпик worktree — это эпик взятых им задач**, а не имя ветки или папки. Сводка, `pm ready` и строка
  фокуса сужаются до него.
- **Задача без эпика общая** для репозитория и видна во всех направлениях. `--epic ""` создаёт такую намеренно.
- **Свежий worktree**, который ещё ничего не взял, получает сводку с одной готовой задачей на эпик
  с пометкой `(APP-12)` и без чужого фокуса. `pm ready` в нём показывает все готовые задачи с пометками.
  Своё направление worktree начинает с `pm task new --epic <KEY>`.
- **Зависимости могут пересекать эпики.** Задача готова, когда выполнены её зависимости, где бы они ни были.
- **Фокус в `PLAN.md` — одна строка на эпик:** `- APP-12: parser done, validation next`.
- **Закрытие автоматическое.** Когда у эпика не остаётся открытых задач, его карточки уходят из колонок
  и переходят в `Archive` группой карточек, которые по-прежнему раскрываются (Log, ветка, PR, дата
  закрытия). Эпик, все задачи которого отброшены, просто исчезает с доски. Архивировать вручную ничего не нужно.
- **Done остаётся коротким.** На доске с эпиками колонка Done держит последние 5 задач, закрытых
  за 20 дней; более старые уходят в группу `Done earlier` раздела `Archive`.
- `pm epics` показывает все направления: открыто/всего и строку фокуса.

Доски без эпиков работают ровно так же, как до появления эпиков.

**Как ложится эпик из трекера.** Ключ эпика в трекере становится эпиком на доске. Одна задача на доске —
одна ветка или merge request: большой тикет делится на несколько задач, несколько мелких тикетов
объединяются в одну. Ключи тикетов пишите в заголовках, ссылки на трекер кладите в `--links`. Трекер
остаётся представлением для команды, доска — рабочей памятью Claude по этой работе.

## Когда использовать и когда нет

Кладите работу на доску, если верно **хоть одно**:

- она переживёт текущую сессию (`/clear`, завтра, следующая неделя);
- её продолжат в другом worktree или на другой машине;
- она ждёт чего-то вне кода: ревью, ответа, другой команды.

Типичные случаи:

| Работа | Что на доске |
|---|---|
| Фича на несколько merge request | один эпик, 5–15 задач, ссылка на план |
| Один тикет, один merge request | одна задача, эпик = ключ тикета или без эпика |
| Рефакторинг в несколько заходов | эпик-слаг вроде `refactor-forms` |
| Фикс на одну сессию, ревью, вопрос | ничего; на напоминание Stop-хука ответить «нечего трекать» |

Если мелкий фикс ушёл во вторую сессию, заведите задачу тогда. Это дешевле, чем заводить заранее.

## Закрытие сессии

Скажите `/close` (или «слил», "wrap up"). Команда оставляет доску в состоянии, с которого следующая сессия
стартует без этого разговора. Четыре шага, по одному обмену на каждый, каждый шаг заканчивается вызовом CLI:

1. **Задачи этого worktree.** По каждой открытой задаче, взятой здесь, Claude спрашивает: готово, ждёт
   мерджа или пауза? Готово или ждёт мерджа — процедура `/done`, она описана ниже. Пауза записывается с
   конкретным следующим шагом: `pm log T-003 --did "…" --next "<точный следующий шаг>"`. Без конкретного
   `next:` задача не считается записанной. Если задачи не взято, а код менялся, Claude предложит завести
   её или примет «трекать нечего».
2. **Ретро.** Скилл `retro` ищет выводы этой сессии (см. [Выводы](#выводы)). Он заканчивается вызовами
   `pm learn add …` по каждому выводу или `pm learn none <id>` для каждой задачи, которая ничему не научила.
   Затем `pm learn check <ids>` по задачам из шага 1 должен напечатать `ok`, иначе `/close` дальше не идёт.
   `/close --no-retro` пропускает скилл и сам запускает `pm learn none`, чтобы отметка о ретро всё же была.
3. **Следующая задача.** `pm ready`, затем вы говорите, с какой задачи начнётся следующая сессия (по
   умолчанию первая готовая, либо «никакой»). `pm next <id>` отмечает её. Если сдвинулся `## Current focus`
   этого эпика, обновляется `PLAN.md`.
4. **Итог.** Четыре строки: строка об изменениях доски; `next session: <id> <title>`; можно ли удалять
   worktree (чисто и запушено) или что не закоммичено и не запушено; и что `/clear` безопасен.

`/close` никогда не удаляет worktree, не пушит код и не запускает git-команд, которые меняют репозиторий.
Удалить worktree — ваше дело.

### Закрытие одной задачи: `/done`

Когда работа закончена, скажите `/done` (или «готово, закрываем»). Claude сначала сверяет разговор:
чек-лист закрыт, проверка действительно прошла. Затем запускает `pm done`, и та печатает, что произошло:

```
$ pm done T-042 --did "сравнил два парсера, выбрал csv-parse"
T-042 → done: no PR or commits, nothing to merge

$ pm done T-041 --did "импорт CSV, тесты зелёные"
T-041 → review: #15 not merged yet; closes by itself after the merge (git config pm.autoClose false turns that off)
```

Задача ждёт мерджа, если у неё есть `pr` или привязанные коммиты. `--pr <url>` сначала записывает PR,
`--no-merge` закрывает сразу. Если что-то не доделано, Claude называет это, заводит остатки задачами и
записывает точный следующий шаг.

Задача в `review` закрывается сама, как только виден её собственный мердж: на одном из следующих стартов
сессии или сразу через `pm reconcile`. Мердж виден двумя способами:

- коммит в основной ветке, в заголовке которого есть задача: `feat(T-041): …` или `[T-041] …`
  (текст коммита не считается);
- forge: `gh` / `glab` сообщает, что PR задачи влит в основную ветку. Это идёт в фоне (не больше
  5 запросов за прогон, никогда во время старта сессии) или сразу через `pm reconcile`.
  Запросы идут только на хост origin: `pr` на другом хосте показывается, но не проверяется. Без `gh` / `glab`
  запросы встают на паузу на 24 часа, а fetch основной ветки продолжается.

Мердж, случившийся до `pm done` (первый из двух PR), задачу не закрывает. Смёрженные задачи, которые не
отметили готовыми, только перечисляются (`Merged, still open`), и Claude спрашивает, прежде чем их закрыть:

```
$ pm reconcile
checked 3 of 3 tasks with a PR or branch
Closed: T-041 (#15)
Merged, still open: T-038 (#10) — close the confirmed ones: pm reconcile --yes <ids>, or pm set <id> status=done
Merge not checked: T-044 — gh is not installed — fix: install gh, run gh auth login, then pm reconcile
$ pm reconcile --yes T-038
Closed: T-038 (#10)
```

Каждая строка об ошибке говорит, что случилось, почему и какой командой это исправить.
`git config pm.autoClose false` превращает любое автоматическое закрытие в вопрос. Если `origin/HEAD`
не задан, основной веткой считается `main` или `master`, и `pm reconcile` один раз печатает исправление:
`git remote set-head origin -a`.

**Обновление.** Обновите все машины, которые делят доску: старая версия покажет `bad status "review"`
в строке проблем доски и не выведет карточки `review` в `BOARD.md` и `board.html` (файлы задач
останутся). Чтобы откатиться, сначала выполните `pm set T-NNN status=in_progress` для каждой задачи в
`review`. После обновления один раз запустите `pm reconcile`: он найдёт задачи, смёрженные раньше, но так
и не закрытые.

## Выводы

`decisions.md` хранит решения. Вывод (learning) хранит урок: «эта ошибка значит X, делай Y». В нём три
части: симптом так, как его увидит следующий агент, исправление и как его применять. Выводы принадлежат
проекту: тот же репозиторий доски, та же синхронизация.

Каждый вывод — файл `learnings/L-NNN.md`:

```markdown
---
id: L-003
title: CI translation keys fail while local passes
pattern: i18n.missing-key-in-ci
status: active            # active | promoted | retired
seen: 2
first: 2026-10-01
last: 2026-10-22
tasks: [PM-012, PM-019]
promoted_to: ""           # "<file>#<section>" once promoted
retired_why: ""
---
## Symptom
Unable to find … <key> in the DOM only in CI.

## Fix
The CI build runs with a stale locale bundle; rebuild locales before the e2e job.

## Apply
When a test fails on a translation key that exists locally: run `pnpm locales:build` first, do not
touch the component.
```

`pm learn` пишет frontmatter; три раздела заполняются из флагов и потом могут правиться вручную.

| Команда | Что делает |
|---|---|
| `pm learn add --title T --pattern area.symptom [--symptom S] [--fix F] [--apply A] [--tasks T-001]` | Записать вывод. `pattern` — это `area.symptom` строчными буквами |
| `pm learn list [--all]` | Активные выводы; `--all` добавляет promoted и retired |
| `pm learn show L-003` | Файл |
| `pm learn find <words…>` | Поиск по заголовку, pattern и тексту активных выводов |
| `pm learn promote L-003 --to <file#section>` | Пометить как повышенный до правила (см. ниже) |
| `pm learn retire L-003 --why "…"` | Вывод оказался неверным или устарел |
| `pm learn none <task-id>` | Отметка ретро, когда ничего не узнали |
| `pm learn check <task-ids>` | `ok` или задачи, за которыми ещё есть строка ретро (код выхода 1) |

**Дедупликация по `pattern`.** Известный pattern считается, а не дублируется:

- тот же pattern, что у активного вывода, увеличивает `seen`, ставит `last` и добавляет задачи; нового файла нет;
- повтор для той же задачи в тот же день ничего не делает, поэтому `seen` считает записи, а не повторные попытки;
- вывод в `retired` с таким pattern снова становится активным;
- вывод в `promoted` не трогается, а команда печатает, куда он был повышен;
- точного совпадения нет: файл создаётся, с подсказкой `similar:`, если совпал префикс `area.` или слово из заголовка.

**По умолчанию не записывать ничего.** Вывод стоит файла, только если иначе следующий агент наступит на те
же грабли. Ретро раскладывает каждого кандидата, срабатывает первое подходящее правило: скилл, который
дал сбой, чинится, а не записывается; то, что уже есть в репозитории, git, CLAUDE.md или скилле, не
дублируется; факт о вас идёт в auto-memory; проверенная процедура из двух и более шагов становится
скиллом; урок проекта становится выводом; дефект кода по всему репозиторию становится задачей. Не
записывается никогда: состояние сессии (номера MR, число тестов, статусы), «X не работает» без
исправления, разовые рассказы, пути и токены конкретной машины. Перед записью текст проверяется на секреты.

**В сводке сессии.** Строка `Learnings:` перечисляет до 5 активных выводов (по задачам этого worktree,
иначе самые свежие), читая только frontmatter, поэтому сводка не растёт вместе с их числом. Строка
`Promote:` появляется только когда вывод встретился 3 и более раз в 2 и более задачах.

**Повышение до правила.** Повторяющийся вывод может стать правилом в репозитории. Claude предлагает цель
(CLAUDE.md или AGENTS.md репозитория либо скилл этой области) и правило в один абзац. Только после вашего
«да» он записывает правило туда с завершающей строкой `Source: L-003`, затем запускает `pm learn promote
L-003 --to <file#section>`. Изменение в репозитории — ваш коммит. Сам Claude ничего не повышает.

**Лимит.** Не больше 100 активных выводов на проект; `pm learn add` отказывает на сто первом, пока вы не
отправите один в retired или не повысите (`pm learn list` их показывает).

**Выводы и auto-memory.** Выводы — это уроки этого проекта. Auto-memory Claude Code остаётся местом для
фактов о вас и ваших предпочтениях. Здесь она не меняется.

## Аудит

`pm audit` перечисляет то, что устарело. Он детерминированный, обходится без LLM и только сообщает: код
выхода 0, и ничего не меняется, пока вы не добавили `--fix`. Если сообщать нечего, печатает `audit: clean`.
Каждая находка — одна строка: `<code> <id or file> — <what> — <fix or how>`.

| Код | Находка | `--fix` |
|---|---|---|
| `stuck` | `in_progress`, у которой последняя ручная строка Log (`did:`) старше 14 дней; строки `auto:` не считаются; нет строк Log → `updated` | нет — только список |
| `waiting-long` | `waiting_since` (или `updated`, если его нет) старше 30 дней | нет — только список |
| `review-no-pr` | `review` без `pr` | нет — только список |
| `dead-worktree` | запись в `worktrees:`, которую не знает `git worktree list` этого репозитория | да, только пока sync выключен: worktree других машин здесь не видны, поэтому при включённом sync запись только перечисляется |
| `orphan` | `in_progress` без записи в `worktrees:` (её worktree удалили после `/close`) | нет — список с подсказкой «pm claim или pm set status=todo» |
| `learning-dup` | два активных вывода с одним `pattern` | нет — только список |
| `next-stale` | `next:` старше 30 дней или на задаче, которая уже не `todo` | да — снять отметку |
| `state-old` | `.state/session-*.json` старше 7 дней | да — удалить |
| `learning-unused` | активный вывод с `last` старше 90 дней | нет — список с подсказкой `pm learn retire` |
| `learning-promote` | активный вывод, перешагнувший порог повышения | нет — только список |
| `learnings-cap` | больше 80 активных выводов | нет — список с числом |
| `decision-dropped` | решение, у которого все `- tasks:` в `dropped` | нет — только список |
| `retro-missing` | задача `done`/`review`, дата последнего статуса которой (последняя строка Log, иначе `updated`) не раньше `retroSince` и не старше 30 дней, без строки `retro:` | нет — только список |

`pm audit --fix` трогает только то, что не может быть ошибкой: записи о мёртвых worktree (при выключенном
sync), устаревшие отметки `next` и файлы состояния сессий старше 7 дней. Он печатает, что изменил, и
коммитит `pm: audit --fix`. Статусы он не меняет и задачи, выводы и решения не удаляет. Всё остальное —
вопрос к вам, а ответ даёт команда, которую называет строка.

При старте сессии, раз в 7 дней, сводка добавляет `[pm] audit: N findings — run: pm audit`, если число
больше нуля. Этот подсчёт ничего не чинит.

## Где что лежит

```
~/.claude/projects/<repo-key>/pm/          ($CLAUDE_CONFIG_DIR/projects/…, если задан)
├── PLAN.md          цель, майлстоуны, текущий фокус (строка на эпик), changelog
├── tasks/T-NNN.md   frontmatter + Goal, Understanding, Checklist, Log
├── decisions.md     только дописывается: D-NNN — что, почему, что отвергли
├── learnings/L-NNN.md   по уроку в файле: симптом, исправление, как применять
├── config.json      префикс номеров задач, startNumber, retroSince
├── memory/          auto-memory Claude Code, только при включённом sync
├── BOARD.md         генерируемое представление, не править
└── board.html       генерируемый канбан, обновляется сам
```

- **Одна доска на репозиторий.** Ключ берётся от общей git-директории, поэтому все worktree репозитория
  делят одну доску, а ветки на неё не влияют.
- **Это git-репозиторий** (ветка `pm`). Каждое изменение — коммит, любое можно отменить:
  `git -C <pm dir> log --oneline`, затем `git -C <pm dir> revert <sha>`.
- **Слои памяти, у каждого своё место:** auto-memory хранит устойчивые факты о проекте; `decisions.md` —
  почему сделано так; `learnings/` — уроки этого проекта; файл задачи — что и как по этой работе; `PLAN.md` — где мы сейчас. Подробный
  план направления — отдельный файл, на который ссылаются через `--links`.

Файл задачи:

```markdown
---
id: T-003
title: CSV import
status: in_progress
order: 30
depends_on: [T-001]
waiting_on: ""
worktrees: [feature-csv]
milestone: M1
links: [docs/plans/csv-import.md]
updated: 2026-09-12
epic: APP-12
---
## Goal
## Understanding
## Checklist
## Log
- 2026-09-12 · feature-csv · did: tokenizer and header mapping · next: handle empty rows
```

При необходимости появляются ещё два поля frontmatter. `next: <date>` отмечает задачу `todo`, с которой
начнётся следующая сессия (ставит `pm next`, снимает `pm claim` или любой уход из `todo`).
`waiting_since: <date>` ставится, когда задача переходит в `waiting`, и снимается, когда выходит из него.
В `config.json` лежат префикс номеров, `startNumber` (из `pm prefix --start`) и `retroSince` — дата
первого ретро на этой доске: аудит требует строки `retro:` в Log только у задач, закрытых в эту дату или позже.

## Синхронизация между машинами (по желанию)

Пока вы не включили синхронизацию для проекта, ничего не покидает вашу машину.

1. Скажите **«включи синхронизацию доски»** (или `pm sync on`). Claude покажет remote и ветку и дождётся «да».
2. Доска отправляется в ветку `pm` собственного remote проекта. Auto-memory Claude Code для проекта
   переезжает внутрь доски и синхронизируется вместе с ней.
3. Дальше каждое изменение доски отправляется в фоне, а каждая сессия сначала делает pull.
   Если коммиты не отправлены больше суток, сводка об этом скажет.
4. На другой машине: установите плагин, откройте проект, скажите **«подключи доску»**.

**Приватность.**

- Если репозиторий проекта публичный, доска и память станут публичными. Используйте
  `pm sync on --remote <private-url>`.
- Синхронизировать доску, а память оставить локальной: `git config pm.syncMemory false` **до** включения sync.
- `pm sync off` выключает синхронизацию и оставляет локальную доску. Ветка на remote остаётся, пока вы её не удалите.

**Конфликты.** В сводке появится `[pm] sync conflict in …`. Claude действует по протоколу: запускает
`pm sync`, сливает перечисленные markdown-файлы с сохранением обеих сторон и синхронизирует снова.
Ничего не теряется.

## Совместная работа с другими инструментами

- **Инструменты для планов** (superpowers, gstack, plan mode, dev-cycle): подробный план пишите ими. Когда
  файл сохранён, Claude добавляет на доску крупные задачи со ссылкой на него и не копирует содержимое.
  Пункты, убранные из плана, становятся `dropped`.
- **Другие инструменты памяти и возобновления** (чекпоинты, context-save скиллы, memory MCP серверы):
  когда доска заработает, подумайте об их отключении, чтобы на «где остановились?» был один ответ.

## Решение проблем

| Симптом | Что делать |
|---|---|
| Нет сводки при старте сессии | У репозитория ещё нет доски. Начните многошаговую работу или скажите «создай доску» |
| `[pm] this repo has a shared board …` | Sync включён на другой машине. Скажите «подключи доску» |
| Изменения плагина не видны | Полностью перезапустите Claude Code. Проверьте версию в `~/.claude/plugins/installed_plugins.json` |
| В сводке `focus: —` | У worktree ещё нет эпика, или в `PLAN.md` нет строки для него |
| Stop всё время просит обновить доску | Запишите прогресс, возьмите задачу или ответьте «нечего трекать» |
| `[pm] board problems: …` | Запустите `pm validate` и исправьте перечисленные задачи |
| Неверное изменение доски | Скажите «отмени правку доски» или отмените его через git в папке доски |
| Код задачи надо убрать | Скажите «откати код T-007»: вы получите точные команды и риски до того, как что-то выполнится |

## Разработка

```
node --test              # запустить все тесты
claude --plugin-dir .    # попробовать плагин из этой копии без установки
```

Как выпустить изменение в установленный плагин:

1. Закончите изменение и прогоните тесты.
2. **Поднимите `version` в `.claude-plugin/plugin.json` самой последней правкой**, затем закоммитьте и
   запушьте. `plugin update` сравнивает только версию. Фоновое обновление маркетплейса может скопировать
   рабочую копию в момент смены версии, и версия, поднятая посреди работы, установит недоделанный код.
3. Выполните две команды обновления и перезапустите Claude Code.
4. Проверьте: версию в `~/.claude/plugins/installed_plugins.json` и что
   `diff -rq ~/.claude/plugins/cache/project-memory/project-memory/<version> .` показывает только `.git`.

Заметки по дизайну лежат в [`docs/superpowers/`](docs/superpowers/).
